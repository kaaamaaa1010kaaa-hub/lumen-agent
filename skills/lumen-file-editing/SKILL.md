# ファイルとコードを直す

## 進め方（単純な1行修正では省いてよい）
1. 見取り図: ファイル一覧・検索系のツールで、対象の規模・構造・関連箇所を把握する。周辺の構造が分からないまま編集しない。
2. 特定: 検索や読み取りで該当する関数・セレクタ・変数を探し、前後を読んでから編集する。一致が複数あると部分編集は失敗する。必要な分だけ周辺の文脈を含める。
3. 編集: 新規ファイルは書き込み、既存ファイルの一部変更は部分編集ツールを使う。全文の書き直しは、無関係な箇所へ影響し、差分も大きくなるので避ける。
4. 検証: 書き込み後に、読み取り系のツールで結果を読み戻す。今書いたツールの成功メッセージは確認にならない。構文チェックやテストを実行できる道具があれば実行する。無ければ、実行していないと報告する。
5. 見直し: 余計な変更や、関連箇所との矛盾が残っていないか確かめてから、結果を伝える。

## コードの書き方
- 「…」「（中略）」「以下省略」は使わない。全文を求められたら完全なコードを出す。省略はそのままでは動かないコードを渡すのと同じ。
- 1回で書ききれなくても、手を抜かず続ける。
- 変数の重複定義、未使用の import、呼び出し側と定義側のシグネチャ不一致、null / undefined の扱い漏れを、読み返して確かめる。
- 修正は場当たりの1行差し替えで終えない。同種の問題が他にも残っていないか、関連範囲まで見る。
- 編集後のコードは、最初からその内容だったかのような自然な形にする。「ここを修正」「Fix: 〜」のような作業履歴のコメントを書き足さない。
- 依頼された方針が実情と食い違うと分かったら、理由を示して代案を出す。計画どおりで問題なければ、無理に別解を探さない。

## 実行・検証の道具
- 実行できないコード（HTML / CSS / JSON など）の健全性は、静的チェックの道具があればそれを使う。
- CSV / JSON などの集計・件数・重複の確認は、目視や記憶で数字を語らず、実行して確かめる。
- 既に分かっている URL の中身は、fetch 系のツールがあればそれで取る。キーワードで探すなら検索。

## 報告
- 何を・どこを・なぜ変えたかを簡潔に書く。変更の要約（パス、増減行、残った警告）で足り、コード全文の再掲は不要。
- 確認できていない項目は、確認していないと書く。
